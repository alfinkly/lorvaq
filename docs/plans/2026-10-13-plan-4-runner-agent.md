# lorvaq — план 4: агент на хостах раннеров

**Цель:** администратор добавляет хост в Settings → Hosts, получает готовую команду
`docker run … lorvaq agent`, запускает её рядом с gitlab-runner — и на сцене CI появляются
хост, процесс раннера со слотами, память каждого джоба, диск хоста и вспышки OOM. Агент
только читает docker API и ничего не меняет; к серверу он подключается сам, исходящим
WebSocket, порт на хосте раннеров не открывается.

**Spec:** `docs/design/2026-10-10-core-and-ci-scene.md` — §3.2 (агент), §4.2–4.3 (места,
«ждёт лимит», OOM), §5 (Settings → Hosts), §6.3 (join-токены — только хэш), §7
(`/api/v1/agent/connect`), §9 (агент офлайн).

## Решения и отклонения от spec

1. **Номер слота агент назначает сам.** Spec брал номер из имени контейнера
   (`…-concurrent-N-…`), но в gitlab-runner это номер параллельной сборки *одного проекта
   на одной регистрации*, а не слот процесса: два проекта получат одинаковый `concurrent-0`.
   Агент держит устойчивое распределение «джоб → наименьший свободный слот» и освобождает
   слот, когда контейнеры джоба исчезли. Имя контейнера не читается вовсе.
2. **Метки — только те, без которых нельзя.** `com.gitlab.gitlab-runner.job.id` (обязательна:
   по ней контейнер вообще считается контейнером джоба), `com.gitlab.gitlab-runner.type`
   (`service` → сервис джоба, остальное — сборка; нет метки — сборка),
   `com.gitlab.gitlab-runner.runner.id` (короткий токен регистрации; нет — пусто). Всё прочее
   агент игнорирует. Разбор меток — в одном модуле с тестами.
3. **Числовой id раннера агент не знает** — в метках только короткий токен. Сервер узнаёт его
   по джобу: GitLab сообщает `runner { id }` у каждого выполняемого джоба. Редьюсер сцены
   заполняет `runner_id` слотов по своим джобам и запоминает соответствие «короткий токен →
   id», чтобы перевести `limit` из метрик (они помечены токеном) в лимиты по id. Новых полей
   GraphQL нет — запросы плана 3 проверены на живом GitLab и не меняются.
4. **Процесс** — один gitlab-runner на демон docker (обычный случай; rootless — у каждого
   пользователя свой демон и свой агент). Ключ процесса — `--process` (по умолчанию
   `gitlab-runner`). Вместимость: `gitlab_runner_concurrent` из `--runner-metrics`, иначе из
   настроек сцены (`capacities` по ключу, `default_capacity`).
5. **OOM** — событие docker `oom` у контейнера джоба, либо `die` с `OOMKilled` в inspect;
   код 137 сам по себе OOM не считается (так же выглядит `docker kill`).
6. **Память джоба** — сумма по его контейнерам: `usage − inactive_file` (как `docker stats`);
   лимит — сумма лимитов, если лимит есть у каждого контейнера; лимит, равный всей памяти
   хоста, означает «без лимита».
7. **Диск** — `statvfs` пути `--disk-path` (по умолчанию `/` контейнера агента: это overlay
   на разделе данных docker).
8. **Идентичность агента — имя из join-токена.** Администратор задаёт имя при создании
   (`[a-z0-9][a-z0-9._-]{0,39}`). Поле `agent` в отчётах сервер всегда ставит сам: агент не
   может выдать себя за другой. Метка хоста (`--host-label`, по умолчанию hostname) приходит
   в `hello`; два агента с одной меткой делят хост на сцене.
9. **Одно подключение на агента.** Новое закрывает старое. Отзыв токена закрывает
   подключение сразу. Нет сообщений 10 с или соединение закрыто → `AgentGone` (процесс
   серый, джобы остаются по данным GitLab).

## Протокол (JSON в текстовых кадрах WebSocket)

`GET /api/v1/agent/connect`, заголовок `Authorization: Bearer <join token>`. Неверный токен —
401 до апгрейда.

- агент → сервер: `{"type":"hello","host":"build-01","version":"0.1.0"}` первым кадром;
  затем `{"type":"report","processes":[ProcessReport…],"disk":{"used_bytes","total_bytes"}|null}`
  раз в 2 с; `{"type":"exit","job_id","oom","exit_code"}` сразу.
- сервер → агент: `{"type":"welcome","agent":"<name>"}` после `hello`.
- Кадр больше 256 KiB, больше 16 процессов или 512 слотов в процессе, двоичный кадр,
  неизвестный тип или отчёт до `hello` — соединение закрывается (код 1008).

`ProcessReport`/`SlotReport` — типы `scenes::ci::input` с новыми необязательными полями:
`SlotReport.runner_token: String` (по умолчанию пусто), `ProcessReport.token_limits:
BTreeMap<String, u32>` (по умолчанию пусто). `runner_id = 0` значит «неизвестен».

## API администратора

- `GET /api/v1/admin/agents` → `[{name, host, version, online, last_seen_ms, created_ms}]`
- `POST /api/v1/admin/agents {name}` → `{name, token, command}` — токен показывается один раз;
  409, если имя занято; 400 — неверное имя.
- `DELETE /api/v1/admin/agents/{name}` → `{"ok":true}`; живое подключение закрывается.

Хранение: таблица `agents (name PK, token_hash UNIQUE, created_ms, last_seen_ms, host,
version)`; `last_seen_ms` обновляется не чаще раза в минуту.

## Агент

`lorvaq agent --server <url> [--join <token>] [--host-label <label>] [--process <key>]
[--runner-metrics <url>] [--disk-path /]`; env: `LORVAQ_SERVER`, `LORVAQ_JOIN` (скрыт в
`--help`), `LORVAQ_HOST_LABEL`, `DOCKER_HOST` (bollard). Переподключение с паузой 1 → 30 с.
Метрики читаются раз в 30 с; недоступные метрики — не ошибка, вместимость из настроек.

## Задачи

1. **Вход сцены:** `runner_token`, `token_limits`; редьюсер заполняет `runner_id` по джобам
   GitLab, учит соответствие токен → id и переводит `token_limits` в `limits`. Тесты в
   `reduce.rs`.
2. **Агент, ядро без сети:** `agent::labels` (разбор меток), `agent::slots` (устойчивое
   распределение), `agent::metrics` (разбор Prometheus-текста: `gitlab_runner_concurrent`,
   `gitlab_runner_limit{runner=…}`), `agent::report` (контейнеры → `ProcessReport`), трейт
   `Docker` + `FakeDocker`. Модульные тесты.
3. **Агент, docker и сеть:** `BollardDocker` (список, статистика, события, inspect),
   `statvfs`, цикл подключения и отправки, `lorvaq agent` в CLI.
4. **Сервер:** миграция `0003_agents.sql`, `Store` для агентов, `agents::Hub` (живые
   подключения, отзыв, `AgentGone`), WebSocket-маршрут, маршруты администратора, сборка в
   `app.rs`. Интеграционный тест: агент с `FakeDocker` подключается к живому серверу,
   хост и слот появляются на сцене, отзыв токена закрывает подключение и сереет процесс,
   чужой токен — 401.
5. **Веб:** Settings → Hosts: добавить хост (имя → команда с токеном, один раз), список
   (онлайн/офлайн, версия, хост, последний контакт), удалить.
6. **README, compose, проверка целиком.**

## Глобальные ограничения

Как в планах 1–3: Rust 1.91, clippy `-D warnings`, fmt, UI на английском со строками в
`web/src/i18n.ts`, время в мс, ни следа конкретных инсталляций. Join-токен — 32 байта из
CSPRNG, в базе только SHA-256; ни API, ни логи его не возвращают (кроме ответа на создание).
Агент ничего не меняет в docker: только list/stats/inspect/events.

## Чего нет в этом плане

Проверка меток на живом раннере (§14 spec) — за владельцем: `docker inspect` контейнера
джоба, сверить три метки выше. Несколько процессов gitlab-runner в одном демоне.
Отдельные стены для разных демонов на одном хосте.
