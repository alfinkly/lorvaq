# lorvaq: ядро и сцена CI — дизайн

Дата: 2026-10-10 · Статус: черновик на ревью · Автор: Alimzhan Kangerey

## 1. Что такое lorvaq

lorvaq — самостоятельное self-hosted приложение для real-time мониторинга через живые
схемы («сцены»). Там, где Grafana показывает значения на осях времени, lorvaq показывает
**вещи в местах, которые движутся**: джоб едет из очереди в слот раннера, бэкап — с диска
в S3, запрос — через сервисы. Цель — с одного взгляда видеть не «сколько», а «почему и
где»: этот джоб ждёт, потому что занят лимит раннера; этот застрял, потому что нет раннера
с нужным тегом; этот слот упал по памяти.

Свойства продукта:

- **Живёт сам.** Свой веб-интерфейс, свои настройки, один docker-образ. Встраивающая
  система (админка, портал) только запускает его и ставит ссылку.
- **Сцены подключаемые.** Сцены встроены в образ и включаются в настройках; каждый
  пользователь включает только нужные.
- **Только чтение.** lorvaq ничего не запускает, не отменяет и не меняет во внешних
  системах.
- **Настраивается из интерфейса.** Подключение GitLab — кнопка Authorize, хосты —
  команда с join-токеном. Через env — только то, без чего приложение не стартует.

Этот документ описывает первый проект: **ядро + сцена CI** (GitLab CI с docker-раннерами).
Следующие сцены (бэкапы, трафик) — отдельные проекты со своими дизайнами.

### Чем lorvaq не является

- Не мониторинг с алертами — это Prometheus/Alertmanager/Grafana.
- Не замена интерфейса GitLab — там разбирают конкретный пайплайн, здесь видна вся система.
- Не платформа плагинов — сцены пишутся в этом репо и выходят с версией образа.

## 2. Модель мира

Любая сцена описывается четырьмя понятиями. Ядро хранит их и не знает о GitLab.

| Понятие | Что это | Примеры в сцене CI |
|---|---|---|
| **Место** (`Place`) | Где что-то находится. Вложенное: у места есть родитель. Может иметь вместимость. | проект, очередь, «нет раннера», хост, процесс раннера, слот, выход «registry» |
| **Сущность** (`Entity`) | Что движется. Находится ровно в одном месте, имеет состояние и атрибуты. | джоб |
| **Перемещение** | Переход сущности между местами. | очередь → слот → registry |
| **Уровень** (`Level`) | Число относительно предела у места или сущности. | память джоба / лимит, диск хоста / размер |

```text
Place  { id, kind, parent?, label, capacity?, attrs }
Entity { id, kind, place, state, attrs, since }
Level  { owner (place | entity), metric, value, max? }
Event  { seq, ts, scene, kind, entity?, from?, to?, attrs }
```

Виды событий: `appeared`, `moved`, `state_changed`, `level`, `flash` (разовое
происшествие, например OOM), `gone`, `stale` / `fresh` (данные источника устарели /
снова свежие).

**Снимок** (`Snapshot`) = все места, сущности и уровни сцены + `seq` последнего
события. Клиент берёт снимок, затем читает события после `seq`.

Сцена = **источники** (откуда данные) + **редьюсер** (как данные превращаются в
изменения мира) + **раскладка** (как мир рисуется). Редьюсер — чистая функция
`(World, Input) -> (World, Vec<Event>)`: так её легко тестировать и прогонять на
записанных данных.

## 3. Компоненты

Один Rust-крейт, один бинарник, один docker-образ `ghcr.io/alfinkly/lorvaq`:

- `lorvaq server` — сервер: источники, редьюсеры, история, HTTP, интерфейс.
- `lorvaq server --demo` — то же, но источники заменены симулятором; база не нужна,
  история в памяти.
- `lorvaq agent --server <url> --join <token>` — агент на хосте раннеров.
- `lorvaq admin reset-password` — сброс пароля администратора (через `docker exec`).

```text
 GitLab (GraphQL) ──poll──┐
                           ├─► редьюсер сцены ─► World ─► события ─┬─► Postgres (история)
 агенты (WebSocket) ──push─┘                                        └─► SSE ─► схема в браузере
```

### 3.1 Модули сервера

| Модуль | Ответственность |
|---|---|
| `world` | типы Place/Entity/Level/Event, применение событий, снимок, шина событий (broadcast) |
| `scene` | трейт `Scene`, реестр встроенных сцен, включение/выключение по настройкам |
| `scenes::ci` | источники и редьюсер сцены CI (см. §4) |
| `sources::gitlab` | GraphQL-клиент, OAuth/токен, обновление токена |
| `agents` | приём WebSocket-подключений агентов, join-токены, состояние хостов |
| `store` | Postgres через `sqlx`: миграции, настройки, секреты, история, чистка |
| `http` | axum: API, SSE, статика интерфейса, сессии |
| `auth` | администратор, сессии, режим доступа зрителей |
| `demo` | симулятор входов для сцены CI |

Трейт сцены (набросок):

```rust
trait Scene {
    fn id(&self) -> &'static str;             // "ci"
    fn reduce(&mut self, world: &mut World, input: Input) -> Vec<Event>;
    fn tick(&mut self, world: &mut World, now: Instant) -> Vec<Event>; // таймауты, «устарело»
}
```

### 3.2 Агент

Запускается контейнером **внутри того же docker-демона, что и раннер** (в случае
rootless — в демоне пользователя раннера), и видит только этот демон. Ничего не меняет.

- Через docker API (`bollard`) находит контейнеры джобов по меткам, которые ставит
  gitlab-runner (`com.gitlab.gitlab-runner.job.id`, `...type` и т.п.), и номер слота
  из имени (`...-concurrent-N-...`).
- Раз в 2 с отправляет отчёт: контейнеры джобов и сервисов, их память и лимиты, номер
  слота, job id, свободное место на диске данных docker (`statvfs` собственного корня).
- Сразу отправляет docker-события `die` с кодом выхода и флагом `OOMKilled`.
- Если указан `--runner-metrics <url>` (эндпоинт метрик gitlab-runner), читает оттуда
  `concurrent` и `limit` по регистрациям. Без него вместимость задаётся в интерфейсе.
- Подключается к серверу **исходящим** WebSocket и переподключается с экспоненциальной
  паузой. Порт на хосте раннеров не открывается.

Точные имена меток и формат имени контейнера проверяются на живом раннере в первой
задаче плана; агент не должен полагаться на непроверенные поля.

## 4. Сцена CI

### 4.1 Источники

**GitLab GraphQL** (scope `read_api`):

- каждые 3 с: `jobs(statuses: [PENDING, RUNNING])` — id, name, stage, status, tags,
  queuedAt, startedAt, runner { id }, project { fullPath }, pipeline { id };
- каждые 3 с: недавно завершённые джобы (статусы success/failed/canceled, первая
  страница по убыванию), чтобы поймать завершения между опросами;
- каждые 60 с: `runners` — id, description, runnerType, status, tagList, runUntagged,
  managers { systemId, status }.

Джобы раннеров уровня инстанса видит только администратор GitLab. Мастер подключения
проверяет права (`currentUser { admin }`) и предупреждает, если видно не всё.

**Агенты** — отчёты и docker-события (см. §3.2).

### 4.2 Отображение на модель мира

| Место | Откуда |
|---|---|
| `project:<path>` | проекты, у которых были джобы за последние 6 ч; сверх 8 самых активных — одно место «другие» |
| `queue` | джобы PENDING, для которых есть подходящий раннер |
| `stuck` | джобы PENDING, которые не возьмёт ни один онлайн-раннер (см. §4.3) |
| `host:<agent>` | хост, подключённый агентом |
| `process:<systemId>` | процесс gitlab-runner; несколько регистраций одного процесса делят его слоты |
| `slot:<systemId>:<N>` | слот процесса; вместимость = `concurrent` |
| `exit:<id>` | выходы из настроек сцены (например «registry», «prod») |

Связка процесса с хостом: агент сообщает runner id из меток контейнеров → GraphQL даёт
`managers.systemId` этого раннера → процесс помещается в хост агента. Процесс без
агента показывается отдельно, без слотов (только счётчик выполняемых джобов).

Сущность `job:<id>`: состояния `pending`, `waiting_limit`, `stuck`, `running`,
`success`, `failed`, `oom`, `canceled`. Уровни: `mem` у джоба (сумма build- и
service-контейнеров / сумма лимитов), `disk` у хоста.

Выходы: правила в настройках сцены — `{exit, match: {stage?, name?}}` (регулярные
выражения). Завершившийся успешно джоб, подошедший под правило, «улетает» в выход;
остальные гаснут на месте. По умолчанию выходов нет.

### 4.3 Причины

- **«нет раннера»** — PENDING-джоб, теги которого не покрывает ни один онлайн-раннер:
  нужно `job.tags ⊆ runner.tagList`, а для джоба без тегов — `runUntagged`. Учитывается
  тип раннера: проектный/групповой берёт джобы только своих проектов/групп.
  Защищённые ветки (`ref_protected`) в первом проекте не учитываются — это записано как
  известное ограничение.
- **«ждёт лимит»** — PENDING-джоб, который подходит раннеру, у процесса которого есть
  свободный слот, но регистрация упёрлась в свой `limit` (известен из метрик
  gitlab-runner). Без метрик это состояние не выводится — джоб просто в `queue`.
- **OOM** — docker-событие `die` с `OOMKilled=true` (или код 137 при лимите памяти)
  у контейнера джоба → `flash` на слоте и состояние `oom`.

### 4.4 Раскладка

Слева направо: проекты → очередь (+ зона «нет раннера» под ней) → хосты с процессами и
слотами (у слота — заливка памяти и маленький блок сервиса, если он есть) → выходы.
Внизу каждого хоста — уровень диска. Процессы разных пользователей на одном хосте
разделены стеной, если агенты сообщили разные демоны. Цвет токена — проект (фиксированная
категориальная палитра, «другие» — серый), обводка — причина ожидания.

При очереди длиннее 40 джобов показывается 40 токенов и счётчик «+N».

## 5. Интерфейс

React + TypeScript + Vite, собирается в статику и вшивается в бинарник (`rust-embed`).
Отрисовка сцены — SVG + `requestAnimationFrame`: движок с примитивами (контейнер, сетка
слотов, токен, перелёт, бак с уровнем, вспышка) и раскладка сцены поверх них.

Страницы:

- **Сцена** — главная; переключатель включённых сцен; баннер «данные устарели N с» при
  проблемах источника.
- **Настройка при первом запуске** — ввод одноразового кода из лога, создание пароля
  администратора.
- **Настройки** (только администратор):
  - *Источники → GitLab* — мастер подключения (§6.2), статус, переподключение;
  - *Хосты* — «Добавить хост» показывает готовую команду `docker run ... agent --join`,
    список агентов (онлайн/офлайн, версия), отзыв токена;
  - *Сцены* — включение, настройки сцены CI (выходы, вместимость процессов без метрик);
  - *Доступ* — режим для зрителей (§6.1), хранение истории.

## 6. Доступ и секреты

### 6.1 Пользователи

- Один **администратор**: пароль (argon2id), сессия в cookie (`HttpOnly`, `Secure`,
  `SameSite=Lax`). Первый пароль создаётся по одноразовому коду, который сервер пишет в
  лог при первом запуске. Сброс — `lorvaq admin reset-password`.
- **Зрители** — режим в настройках:
  - `open` — схемы видны всем (доверенная сеть, демо);
  - `proxy` — доверять заголовку пользователя от reverse proxy, только с указанных
    адресов (forward-auth перед lorvaq);
  - `admin` — только администратор.
- Настройки и все `admin`-API — только администратору в любом режиме.

### 6.2 Подключение GitLab

Мастер в интерфейсе:

1. URL GitLab.
2. Способ:
   - **Authorize (OAuth 2.0, authorization code + PKCE).** Нужно OAuth-приложение в
     GitLab (Admin → Applications или User settings → Applications): мастер показывает
     redirect URI (`<public url>/api/v1/oauth/gitlab/callback`) и scope `read_api` для
     копирования, принимает Application ID (и Secret для confidential-приложения).
     Дальше — кнопка Authorize. Access token обновляется по refresh token до истечения.
   - **Токен.** Кнопка открывает страницу создания токена в GitLab с заполненными
     именем `lorvaq` и scope `read_api`; пользователь вставляет токен.
3. Проверка: запрос `currentUser`, вывод «видно всё / видно только проекты пользователя».

Подсказка в мастере: авторизуйте служебного пользователя, а не личный аккаунт — иначе
подключение умрёт вместе с аккаунтом.

### 6.3 Секреты

- Env (единственное обязательное): `DATABASE_URL`, `LORVAQ_SECRET_KEY` (32 байта,
  base64). Необязательно: `LORVAQ_PUBLIC_URL` (иначе берётся из настроек или запроса),
  `LORVAQ_LISTEN` (по умолчанию `0.0.0.0:8080`).
- Токены GitLab, client secret, join-токены хранятся в Postgres: токены GitLab и secret —
  зашифрованы (XChaCha20-Poly1305, ключ из `LORVAQ_SECRET_KEY`); join-токены — только
  хэш. Интерфейс и API никогда не возвращают секреты обратно.
- Секреты не пишутся в логи; ошибки GitLab логируются без заголовков и тел ответов.

## 7. API

Версия в пути, `v1` — публичный контракт.

| Метод | Путь | Доступ | Что |
|---|---|---|---|
| GET | `/healthz` | все | живость + состояние источников |
| GET | `/api/v1/scenes` | зрители | включённые сцены |
| GET | `/api/v1/scenes/{id}/snapshot` | зрители | снимок мира сцены |
| GET | `/api/v1/scenes/{id}/events` | зрители | SSE; `Last-Event-ID` для продолжения |
| GET | `/api/v1/agent/connect` | join-токен | WebSocket агента |
| * | `/api/v1/admin/...` | администратор | настройки, источники, хосты, сцены |
| GET | `/api/v1/oauth/gitlab/callback` | — | возврат из OAuth |

Если клиент просит события после `seq`, которых уже нет в буфере сервера (последние
10 000 событий в памяти), сервер отвечает `410`, и клиент заново берёт снимок.

## 8. Хранение

Postgres, `sqlx` с миграциями, встроенными в бинарник и применяемыми при старте.

- `settings` (ключ → JSON), `admin`, `sessions`, `gitlab_connection`, `agents`
  (хэш join-токена, имя, последний контакт), `scene_settings`.
- `events` (`seq`, `ts`, `scene`, `kind`, `entity`, `from`, `to`, `attrs jsonb`),
  индекс по `(scene, ts)`. Хранение 14 дней по умолчанию, чистка раз в час внутри
  сервера.

Живая схема не зависит от базы: если запись в `events` падает, сервер продолжает
показывать схему, копит не больше 10 000 событий в очереди записи и пишет
предупреждение; при переполнении старые события из очереди отбрасываются.

## 9. Ошибки и деградация

| Что сломалось | Что видно |
|---|---|
| GitLab недоступен / 5xx | баннер «данные GitLab устарели N с», токены замирают (никакой выдуманной анимации), опрос с паузой до 30 с |
| токен отозван / refresh не удался | баннер + статус в настройках «нужна повторная авторизация» |
| агент офлайн | хост серый «агент недоступен», память и диск — «нет данных», джобы продолжают отображаться по данным GitLab |
| нет метрик раннера | «ждёт лимит» не выводится; вместимость из настроек |
| база недоступна | схема работает, история не пишется, предупреждение в настройках |
| джоб пропал между опросами | закрывается по списку недавно завершённых; если не найден за 2 мин — `gone` |

## 10. Тестирование

- **Редьюсер сцены CI** — табличные тесты на синтетических входах: появление, очередь,
  «нет раннера», «ждёт лимит», запуск, OOM, завершение, выход, пропажа. Только
  синтетические данные: никаких выгрузок из настоящего GitLab в репо.
- **Ядро** — применение событий к миру, снимок + события = тот же мир, `410` при
  разрыве.
- **GraphQL-клиент** — разбор ответов по фикстурам, сделанным вручную по схеме GitLab.
- **Агент** — разбор меток/имён контейнеров и событий через трейт над docker API с
  фейковой реализацией.
- **Хранение** — интеграционные тесты на Postgres в testcontainers.
- **Интерфейс** — vitest для раскладки и разбора событий; `--demo` используется как
  смоук: сервер в demo-режиме поднимается в CI и отдаёт снимок и события.
- Разработка через TDD; `cargo clippy -D warnings`, `cargo fmt --check`.

## 11. Сборка и релизы

- GitHub Actions: на PR и `main` — тесты Rust и интерфейса, clippy, fmt; на `main` —
  образ `ghcr.io/alfinkly/lorvaq:<sha>`; на тег `vX.Y.Z` — образ `:vX.Y.Z` и `:latest`,
  GitHub Release с digest образа.
- Образ: многоэтапная сборка (node → интерфейс, rust → статический бинарник musl),
  итог на `scratch`/`distroless`, запуск не от root. Пока только `linux/amd64`.
- В репо: `compose.yml` для быстрого старта (lorvaq + postgres) и `compose.demo.yml`
  (только lorvaq с `--demo`).
- Лицензия: MIT.

## 12. Правила публичного репо

lorvaq разрабатывается открыто, а используется в том числе в закрытой инфраструктуре.
В репо **никогда** не попадают:

- имена хостов, IP, домены, URL GitLab и имена раннеров конкретных пользователей;
- скриншоты и записи с реальными данными — только `--demo`;
- выгрузки и фикстуры из реальных GitLab/docker — только синтетика;
- токены, ключи, переменные CI конкретных инсталляций;
- документы о деплое конкретной компании — они живут в репо этой компании.

Защита: `gitleaks` в CI; локальный pre-commit-хук с личным deny-листом шаблонов
(файл вне репо, например `~/.config/lorvaq/denylist`), чтобы сам список не попадал в репо.

## 13. Границы первого проекта

Входит: ядро (модель мира, шина, снимок/SSE, история), сцена CI (GitLab + агент),
интерфейс со сценой, настройками и мастерами, администратор и режимы доступа, demo-режим,
образ и релизы.

Не входит (следующие проекты): перемотка истории, «созвездие» пайплайна, искры
egress, сцены бэкапов и трафика, описание сцен конфигом, OIDC, учёт `ref_protected`,
multi-arch образ, внешние плагины.

## 14. Риски

- **Метки контейнеров gitlab-runner** могут отличаться между версиями — проверяются
  первой задачей плана на живом раннере; разбор изолирован в одном модуле агента.
- **Сетевые ограничения на хостах раннеров** (egress-правила для пользователя раннера)
  могут не пустить агент к серверу — агенту нужен узкий разрешённый адрес/порт сервера;
  это настраивается при деплое, документируется в README.
- **Нагрузка опроса GraphQL** — 2 запроса каждые 3 с + 1 в минуту; при росте инсталляции
  интервал настраивается.
- **Права GitLab** — без администратора видны только джобы проектов пользователя;
  мастер честно предупреждает.
